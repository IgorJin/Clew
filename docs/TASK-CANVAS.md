# Project Inbox — минимальная версия Task Canvas

Статус: описание продукта для V1. Дата: 2026-09-11. Релиз не назначен. V1 обозначает первую версию этой возможности, а не релиз Clew v1.0. Имя файла сохранено для существующих ссылок.

## Намерение

На уровне Project появляется простой Inbox для мыслей, проблем и запросов. Пользователь быстро записывает намерение (intent), не составляя Task Contract. Затем по явному запросу Clew сопоставляет выбранные записи с задачами проекта и предлагает следующий шаг: создать задачу, прикрепить к существующей или отметить уже покрытую потребность.

Первый объём — текстовый ввод, список намерений и Suggested plan. Скриншоты, свободный холст и расширенная организация материалов остаются дальнейшим развитием. Проверяем сначала, помогает ли Inbox превращать разрозненные мысли в осмысленные задачи и избегать дублирования.

## Минимальный интерфейс

Project navigation:

```text
Overview   Tasks   Inbox
```

Inbox показывает число открытых намерений, форму быстрого ввода и записи, сгруппированные по дате. Пример интерфейса; номера задач ниже иллюстративны и не задают связи в текущем backlog:

```text
PROJECT INBOX                              7

┌─────────────────────────────────────────────┐
│ Dump an idea, problem or request...          │
│                                             │
│                                    [Add]    │
└─────────────────────────────────────────────┘

TODAY

○ попробовать Open Code Review
  Similar work not analyzed yet

○ разобраться с Codex worktrees
  Related: CLEW-88

○ сделать task screen project-centric
  Related: CLEW-94 · Running

                         [Analyze 3 intents]
```

Add сохраняет текст в выбранном Project без автоматического анализа или запуска работы. Пользователь выбирает намерения; число на Analyze соответствует выбранным записям. До первого анализа связь не считается установленной. Найденная связь показывает задачу, её актуальный статус и доступное объяснение.

После Analyze:

```text
Suggested plan

NEW TASK
Codex workspace isolation investigation
2 intents
[Create]

ADD TO EXISTING
CLEW-94 Project-centric UX
1 intent
[Attach]

NO ACTION
Open Code Review
Already covered by CLEW-103
[Mark resolved]
```

Это примеры видов предложений, не разбиение трёх строк выше: реальный результат обязан показывать конкретные исходные intents каждого предложения. Каждый выбранный intent получает одно предлагаемое действие либо явный статус «недостаточно данных» и остаётся открытым.

## Действия и Task Shaping

| Предложение     | Действие пользователя | Результат                                                                                                                      |
| --------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| New task        | Create                | Открыть предзаполненное создание задачи: проверить название, смысл и критерии; сохранить draft со ссылками на исходные intents |
| Add to existing | Attach                | Прикрепить intents как дополнительный запрос/контекст к выбранной задаче, сохранив происхождение                               |
| No action       | Mark resolved         | Явно закрыть intents как уже покрытые с указанием существующей задачи и объяснением                                            |

Task Shaping в V1 — небольшое уточнение предложения через текущую форму создания задачи. Полноценный визуальный редактор workflow для этого не нужен. Если данных мало, предложение сохраняет вопросы; готовность Task Contract к execution проверяется существующими правилами.

Attach к Running задаче не меняет автоматически утверждённый контракт и не отправляет новые инструкции работающему агенту. Это сохранённый дополнительный запрос, который человек отдельно включает в следующую итерацию или уточнение задачи. Mark resolved закрывает intent, но не принимает результат и не завершает связанную Task.

Анализ только предлагает действия. Принятие каждого предложения явное; повторное нажатие Create/Attach/Mark resolved не создаёт дубли. Закрытые/обработанные intents сохраняются с исходным текстом и ссылкой на принятое действие. Не принятые предложения оставляют записи открытыми. Изменение текста intent или состояния целевой Task требует перепроверки предложения перед применением.

## Граница ответственности Clew

```text
                  PRODUCT WORLD
       human thoughts / issues / manager
                         ↓
══════════════════ CLEW EDGE ══════════════════
                  Project Inbox
                         ↓
                  Task Proposals
                         ↓
                   Task Shaping
                         ↓
──────────────── EXECUTION READY ──────────────
                   Task Contract
                         ↓
                     Execution
                         ↓
                   Verification
                         ↓
                      Review
                         ↓
                  Accepted Change
══════════════════════════════════════════════
```

Project Inbox, Task Proposals и Task Shaping входят в продукт на его входной границе (edge). Execution core начинает работу с проверенного Task Contract. Намерение, анализ и предложение не являются Run и не запускают execution. Accepted Change сохраняет существующую семантику явного принятия результата человеком; Inbox не обходит проверки, review или approvals.

В V1 мысли вводятся вручную. Issues и manager в схеме обозначают возможные будущие источники; интеграции с ними не входят в первый объём.

## На чём строится анализ

Первая версия использует выбранные intents и доступные записи задач текущего Project: контракты, статусы и историю. Анализ ищет общую потребность, связанную текущую работу и уже реализованные результаты. Для каждого совпадения нужны ссылка и краткое объяснение. Похожее название или просто завершённая Task сами по себе не доказывают, что намерение покрыто; неуверенность показывается явно.

По мере развития Clew сможет использовать Project Memory, specs, failures, architecture и execution outcomes. Эти источники — причина встроить Inbox в продукт: предложения могут учитывать фактический опыт работы над проектом. Источник и актуальность найденного контекста должны оставаться видимыми; пока источник недоступен, анализ не заявляет, что использовал его.

[Scout](./SCOUT.md) отвечает за контекст кода и в будущем память репозитория. Inbox отвечает за формулировку потребности и её связь с задачами. Полноценная Project Memory не является условием первого прототипа Inbox; scout можно подключить позже для уточнения предложений и Task Shaping.

## Первый объём и проверка полезности

V1 включает Project tab, текстовый Add, список/выбор intents, явный Analyze, три типа предложений и подтверждение действий со связями происхождения. Нет автозапуска анализа, постоянного наблюдателя, автоматического изменения контрактов или новых execution states.

Проверить на небольшом наборе реальных намерений:

1. Запись сохраняется после reload и видна только в своём Project.
2. Анализ выбранных intents предлагает новую задачу, связь с существующей или покрытие; объяснение можно проверить по источникам.
3. Несколько intents могут сформировать одну задачу без потери исходных текстов.
4. Анализ и Attach к Running задаче не запускают и не перенаправляют execution.
5. После принятия предложения сохранена связь intent → proposal → Task/решение; повтор действия не создаёт дубль.
6. Ошибка анализа, отсутствие совпадений или недостаток контекста оставляют intents доступными для следующего решения.

Полезность оценивается по тому, какие предложения пользователь принял, исправил или отклонил, и помогли ли они избежать дубликатов. Отдельный dashboard аналитики для пилота не требуется.

## Дальнейшее развитие

- Скриншоты, вложения, данные и свободный холст для материалов.
- Более богатое Task Shaping, разбиение на несколько задач и связь с эпиками.
- Подключение Project Memory/scout, specs, прошлых failures и outcomes с проверкой актуальности.
- Внешние источники intents и межрепозиторные сценарии после отдельного проектирования.

Хранение будущих вложений согласуется с [жизненным циклом данных](./TASK-DATA-LIFECYCLE.md). Связанные направления: [эпики](./EPICS.md), [мультирепозиторность](./MULTI-REPOSITORY.md), [UI/UX-агент](./UI-UX-AGENT.md). Реализационные карточки и релиз Inbox назначаются отдельно; текущие scout/storage зависимости этим описанием не меняются.
