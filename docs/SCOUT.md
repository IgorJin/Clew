# Scout: минимальная сущность и дальнейшее развитие

Статус: план scout v0, CLEW-123–126. Дата: 2026-09-10. Релиз не назначен. Это первый эксперимент в очереди контекста задачи; v0.10 Keyboard-first остаётся текущим мини-релизом.

## Назначение

Scout изучает один репозиторий под конкретную задачу и формирует небольшую карту релевантного кода. Архитектор и воркер получают отправную точку: где смотреть, какие компоненты связаны, какие проверки существуют и что осталось неизвестным.

Пользователь намерен расширить scout позже; окончательный вид общей памяти репозитория пока не определён. v0 проверяет полезность выбранного контекста, не фиксируя навсегда способ индексации, хранения или обновления общей карты.

## Граница v0

- Один локальный Project, один репозиторий и один явно выбранный commit. Для первой версии используется read-only представление этого commit; незакоммиченные изменения не объявляются изученными и отображаются как несовпадение со снимком.
- Явный запуск scout для существующей задачи через CLI на текущем поддерживаемом harness. Пример поверхности: `clew task scout TASK`; окончательное имя закрепляется в CLI help при реализации.
- Один ограниченный read-only запуск с timeout/cancel и проверкой structured output. Используются существующие harness adapters; новый агентный цикл и универсальная plugin-система не требуются.
- Чтение исходников, manifest и доступных repo instructions в пределах выбранного репозитория. Scout не меняет исходники, не устанавливает зависимости, не запускает найденные команды тестов и не делает сетевое исследование.
- Результат сохраняется в небольшом versioned JSON-файле в state directory, с checksum и ссылкой от Task; CLI показывает человекочитаемый preview. Это временный простой способ хранения до ArtifactStore, не отдельная универсальная подсистема.
- Выбор готовой карты для следующего architect/worker запуска явный. Создание карты и её выбор сами не запускают основную задачу и не меняют её workflow state.
- Повторное исследование по инициативе пользователя создаёт новую версию карты; прежний результат и идентичность использовавшего его Run сохраняются.

## Минимальный контракт RepositoryContext v1

| Поле          | Смысл                                                                                            |
| ------------- | ------------------------------------------------------------------------------------------------ |
| identity      | schemaVersion, contextId, taskId, projectId, fingerprint публичного Task Contract                |
| source        | repository identity, commit SHA, scope изученных путей, время и идентификатор scout attempt      |
| components    | релевантные пути/символы и краткое назначение                                                    |
| relationships | обнаруженные связи компонентов с указанием источника                                             |
| checks        | существующие команды/файлы проверок и почему они подходят; это рекомендации, не evidence запуска |
| observations  | наблюдаемые факты отдельно от предположений; каждая запись связана с source reference            |
| unknowns      | что не удалось установить, пропущенные области и ограничения исследования                        |
| provenance    | runtime/session reference, статус complete/partial, checksum результата                          |

Source reference содержит repo-relative path, revision и при необходимости диапазон строк/символ. Существование файла и диапазона проверяется локально; это не доказывает семантическую истинность всех выводов агента. Отсутствующее подтверждение остаётся предположением или unknown. Результат scout не меняет Task Contract, permissions, completion policy или review verdict.

Стартовый предел результата — 64 КиБ UTF-8 JSON; числа компонентов/ссылок ограничиваются схемой. Исследование имеет настраиваемый timeout и лимит доступного вывода. При переполнении сохраняется явный partial с omissions, либо операция завершается validation error; нельзя публиковать молча обрезанный complete. Raw transcripts, секреты и скрытые рассуждения не копируются в карту.

## Жизненный цикл и подключение

Запрос получает собственный attempt ID и idempotency key. Повтор одного запроса не запускает второй scout; после crash/interruption состояние явно interrupted/failed и доступен новый явный attempt. Уже опубликованный результат не перезаписывается. Запись файла атомарная; Task reference публикуется после неё. История Run фиксирует contextId/checksum, фактически использованные при запуске.

При использовании проверяются Task fingerprint, Project/repo identity и revision. Смена требований или кода означает stale, а не «всё ещё актуальную память». Для v0 пользователь может заново запустить scout либо явно продолжить без его карты; старая карта не подставляется незаметно. Ошибка опционального scout не должна изменять исходную задачу или делать обычный путь запуска недоступным.

Первый consumer — тонкий дополнительный блок в существующем Execution Brief для architect и worker. Обязательные инструкции и критерии задачи имеют приоритет; контекст scout передаётся как данные с provenance. Контекст задачи может включать выбранную часть карты и ссылку на полный bounded результат. Проверки карты являются подсказками и не считаются выполненными проверками.

В Quick карта идёт worker; в Standard — worker; в Deep — architect и применимым worker stages. Если рабочая revision изменилась в ходе Deep, карту нельзя выдавать за текущую: выполняется проверка применимости, обновление или явное исключение. Автоматическое повторное исследование пока не вводится. Reviewer и QA получат проверенный общий механизм выбора контекста позднее в CLEW-115.

Scout v0 работает локально. Paired path продолжает существующее поведение и явно сообщает, что scout context недоступен на этом host; расширение Runner v1 для пересылки карт/исходников не входит в v0.

## Пилот до фиксации checkpoints

Использовать scout на трёх представительных задачах: локальное исправление, изменение с зависимостью между модулями, задача с неоднозначной областью изменений. Передать карту архитектору/воркеру и записать: какие ссылки помогли, чего не хватило, что оказалось лишним или неверным, размер выбранного контекста и затраты scout. Не утверждать ускорение без сопоставимых измерений.

Fixtures автоматически проверяют контракт, provenance, stale/cancel/restart и совместимость с обычным запуском. Реальные прогоны подтверждают полезность содержания; они не заменяются одной проверкой JSON. Вывод пилота — перечень сохранённых полей и необходимых поправок, включённых в контракт до начала CLEW-114/115. Если результаты неудовлетворительны, карточка пилота остаётся незавершённой до исправления минимальной версии; постоянная память не становится обходным требованием.

Это сокращённая схема: точные зависимости остаются в карточках. Scout не зависит от нового ArtifactStore/checkpoint, чтобы пилот можно было провести первым. CLEW-114 требует завершённого CLEW-126; CLEW-115 наследует эту зависимость. Оптимизация хранения CLEW-105–113 может выполняться независимо от scout. После пилота сначала используется простая карта v0, затем её references переходят в стандартное хранение без повторного исследования и изменения provenance.

## Позднее расширение — намерение, не текущие обязательства

- Общая переиспользуемая карта репозитория между задачами, обновление по diff и проверка устаревания отдельных фактов.
- Повторный запрос к scout во время работы, когда выявлена новая зависимость или недостаток контекста.
- Обновление памяти по завершённой задаче с проверкой revision и источников; выводы агента не становятся общей истиной автоматически.
- Дополнительные способы поиска/индексации, несколько репозиториев, remote execution и plugin capability.
- Политики хранения, compaction и удаления общей памяти отдельно от retention конкретной Task.

Выбор графа, embeddings, базы знаний, фонового сервиса и UX остаётся открытым до отдельного исследования. Для совместимости v0 сохраняет versioned contract, стабильные IDs и source references; эти точки расширения не требуют реализации перечисленных возможностей сейчас.

Память репозитория даёт знания о коде; выбранный контекст задачи связывает эти знания с конкретной работой; [checkpoint](./TASK-DATA-LIFECYCLE.md) хранит прогресс этой работы. Эти три сущности имеют разные сроки жизни.
