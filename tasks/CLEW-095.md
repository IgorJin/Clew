# CLEW-095 — Project domain and lifecycle

## Objective

Introduce the `Project` entity as the top-level domain context Clew executes Tasks inside, with durable persistence, CLI lifecycle commands, Git-repository validation, a stable `Task.projectId` reference, and project-scoped API snapshots. One Project maps to one local Git repository in this release, and the model intentionally leaves that boundary extensible.

## User outcome

A user can add a local folder as a Project through the CLI, see its detected repository metadata, list Projects across daemon restarts, and get a clear diagnostic when the folder is not a Git repository. Every new Task created through the CLI or API is bound to a resolved Project through a stable `projectId`.

## Context

Project-centric UX tasks (`CLEW-096`–`CLEW-098`) consume these contracts. Today Tasks are a global, flat list; routing project metadata through repository paths is unsafe and blocked on purpose. The durable identity is `Project.id`, never a filesystem path.

## Scope

- `Project` domain type: `id`, `name`, `localPath`, `repositoryRoot`, `defaultBranch`, `createdAt`, `updatedAt`, plus a stable internal identifier generated by Clew;
- durable Project persistence with a migration and restrictive storage handling;
- `clew project add <path>`, `list`, and `status` (or equivalent) CLI commands;
- Git validation at add time (repository detection, repository root, default branch detection) with a readable failure for non-Git folders;
- `Task.projectId` on new Tasks created through any CLI/API entry point;
- API and daemon snapshot projection that carries Projects and associates Tasks to them;
- redaction boundaries: Project fields may be rendered in the UI, but local path exposure in public events is limited to what Task records already expose.

## Out of scope

- nested repository discovery inside a folder;
- multi-repository Projects or Tasks;
- remote/GitHub Projects;
- any Web UI work, including the switcher and screens owned by `CLEW-096`–`CLEW-098`;
- changing execution: adding a Project never starts, stops, or modifies running Tasks.

## Deliverables

- domain, migrations, and store changes;
- CLI commands and contract updates;
- fixture coverage for valid and invalid folders;
- API/snapshot schema updates;
- compatibility documentation.

## Acceptance criteria

1. A valid local Git repository can be added and is detected with its repository root and default branch.
2. A non-Git folder is rejected with an actionable error and leaves no partial Project record.
3. Projects survive daemon restart without identity drift.
4. New Tasks carry `projectId`; pre-existing Tasks remain readable through compatibility handling.
5. API snapshots expose Projects and the Task↔Project association without duplicating repository paths as identity.
6. Full release quality gate passes with the new migrations and contracts.
