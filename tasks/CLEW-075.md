# CLEW-075 — Controller and Runner split

## Objective

Separate host execution from the Clew Controller so a self-hosted service can schedule work on one paired local Runner without receiving host credentials or arbitrary filesystem access.

## User outcome

A developer can keep repositories, Git, Codex/OpenCode credentials, and terminal access on their machine while connecting it to a separately running Controller/UI.

## Context

v0.4 has an in-process Runner. v0.5 preserves the same contracts while replacing the in-process call boundary with authenticated, reconnectable transport. The first version intentionally supports exactly one Runner per Controller.

## Scope

- explicit Controller/Runner protocol version;
- one-time pairing token generated by Controller UI/CLI;
- `clew runner register --controller URL --token TOKEN`;
- durable Runner credentials with rotation and revocation;
- authenticated outbound WebSocket from Runner;
- Runner identity, capabilities, version, and heartbeat;
- leased Stage assignment and acknowledgment;
- idempotent command delivery and result/event upload;
- cancellation and disconnect semantics;
- stable `runner_id` on execution records;
- local repositories, credentials, native harnesses, and terminal remain Runner-owned;
- parity mode proving in-process and remote Runner execute the same Task contract.

## Out of scope

- multiple active Runners per Controller;
- load balancing or failover;
- remote terminal streaming through Controller;
- uploading repository contents by default;
- team RBAC.

## Deliverables

- Runner executable/service mode;
- pairing and credential lifecycle;
- Controller transport endpoint;
- lease/idempotency persistence;
- capability and health diagnostics;
- reconnect and security acceptance fixtures.

## Acceptance criteria

1. One paired Runner can execute Quick, Standard, and Deep Tasks.
2. Pairing tokens are single-use; Runner credentials are rotatable and revocable.
3. Duplicate delivery cannot create duplicate Runs or turns.
4. Disconnect during assignment, execution, and result upload has explicit recoverable behavior.
5. Controller never receives native harness credentials or unrestricted host filesystem access.
6. In-process and remote Runner modes produce equivalent durable Task outcomes.
7. A second Runner is rejected with a clear one-Runner-scope error.

## Verification

- transport contract and authentication tests;
- pairing/revocation matrix;
- disconnect/reconnect at every lease phase;
- duplicate and out-of-order delivery tests;
- local-vs-remote acceptance comparison;
- security inspection of normalized outbound records.

## Dependencies and parallelization

Depends on released v0.4 daemon/API contracts. It is the foundation for Docker packaging and should not be parallelized with `CLEW-076` beyond documentation/fixture preparation.

## Risks

- distributed lease semantics can duplicate expensive native work if underspecified;
- Controller/Runner version skew needs explicit compatibility;
- exposing live session UX across host/controller boundary may tempt terminal streaming scope creep.
