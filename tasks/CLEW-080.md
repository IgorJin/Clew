# CLEW-080 — Runner pairing and credential operations

## Objective

Provide a safe operator workflow for pairing exactly one local Runner with a Controller and managing its durable credentials without exposing pairing material in URLs, logs, Task events, or browser state.

## User outcome

A user can pair, inspect, rotate, revoke, and replace the one supported Runner from the CLI and Web UI, with clear diagnostics when either side is offline or incompatible.

## Context

`CLEW-075` owns the transport, protocol, Runner identity, and lease semantics. This task owns the human-facing credential lifecycle and operational projection consumed by the Docker deployment in `CLEW-076`.

## Scope

- single-use, short-lived pairing codes generated by the Controller;
- `clew runner pair`, `status`, `rotate`, and `revoke` commands;
- pairing and Runner-health views in the Web UI;
- durable credential storage with restrictive permissions on the Runner;
- hashed or encrypted Controller-side credential representation;
- explicit protocol/version/capability compatibility diagnostics;
- audited rotation, revocation, replacement, and failed-pairing events;
- redaction across logs, API responses, Task Thread, and browser state;
- one-active-Runner enforcement with an intentional replacement flow.

## Out of scope

- multiple active Runners;
- team identity, RBAC, or shared pairing administration;
- public OAuth or hosted-account login;
- remote terminal byte streaming through the Controller.

## Deliverables

- versioned pairing and Runner-status contracts;
- CLI and Web UI operator flows;
- credential persistence and redaction boundary;
- rotation/revocation/replacement tests;
- compatibility and troubleshooting documentation.

## Acceptance criteria

1. A pairing code succeeds exactly once and expires within its configured bounded lifetime.
2. Runner credentials can be rotated and revoked without exposing either old or new secrets.
3. Revoked credentials cannot reconnect or acknowledge a lease.
4. A second Runner is rejected unless the operator explicitly replaces the current Runner.
5. CLI, UI, API, logs, and durable public events expose only safe Runner identity and health fields.
6. Offline, version-skewed, revoked, and capability-incompatible states produce actionable diagnostics.
7. Restarting either side preserves valid pairing and never resurrects revoked credentials.

## Risks

- pairing codes copied through shell history can become credentials if redemption is not strictly single-use and short-lived;
- credential replacement can accidentally leave two active Runners without one transactional authority boundary;
- browser presentation can leak secrets through generic error rendering.
